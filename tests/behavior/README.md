# 行为测试

> 契约测试证明「注入里写了规则」，行为测试证明「AI 照着做了」。
> 两层都要过，才算这个功能可用。

## 为什么要单独做

`tests/test_crop_cli.py` 和 `dsh/test/index.test.mjs` 是**契约测试**：它们断言注入文本包含哪些规则。
但规则写进去，模型可能照样忽略——2026-11-15 的 mermaid 事件就是例子：协议写着"守住范围"的意思从没进上下文，AI 顺着问题就把支线做成了任务。

所以每个场景都要跑一次真实模型，看**行为**。

## 场景

### S1 · 开工绑定

**注入**：开工提示 + 两条候选工作（README / Panel）
**用户**：`继续吧。`
**期望**：
1. 第一句话确认在做哪一条（或说要新开）；
2. 先绑定（`crop switch` 或 `probe_report`），再谈干活；
3. 不出现「我先看看代码」这类未绑定的动作。

**判据**：`tool_calls` 里必须有绑定动作，`reply` 里必须出现具体 work_id 或明确的新开声明。

### S2 · 支线不扩散

**注入**：`[crop] 当前工作：修复状态行异常（crop-runtime-fix）`
**用户**：`DSH 右侧边栏支持 mermaid 渲染吗？`
**期望**：
1. 一句话回答问题（支持/不支持）；
2. 记为支节（`crop side`）或明确说「这是支线」；
3. **不**给安装命令、**不**展开方案、**不**把它变成新任务；
4. 最后一句话回到当前工作。

**判据**：`tool_calls` 含 `crop side`（或等价的枝节记录）；`reply` 不含 `plugin add` / `npm install` / 长篇方案。

## 跑法

用两个独立模型实例，喂同样的协议与注入，要求输出：

```json
{"reply": "...", "tool_calls": [{"name": "...", "args": {}}], "rationale": "..."}
```

然后按上面的判据逐条勾。结果写进 `RESULTS.md`，附上场景、输出、判定。

## 失败的常见原因

| 现象 | 说明什么 |
|---|---|
| 直接回答，不绑定 | 协议里的绑定条款不够硬，或被当成背景信息 |
| 回答了还顺手给方案 | 支线条款不够硬，或缺少「不展开」的默认动作 |
| 绑定了但绑错工作 | 候选列表缺少足够信息（goal 太短） |
