# 注入文案清单与评价（2026-11-15）

> 每个注入点：触发条件 → 当前实际文案 → 期望 AI 做什么 → 问题 → 建议文案。
> 评价标准：短（≤ 80 字）、只讲要做什么、不重复、不误导。

## 先修三条评论

### C1 · ask-human 要记起止两个时间

- **错在哪**：只记了“工具返回后”一个点，算不出这次等人类的真实时长
- **改法**：`human_wait` 拆成 `human_wait_start`（AI 调 ask-human 工具时）与 `human_wait_end`（工具返回时），成对出现
- **落盘**：`{"ev":"human_wait","sid":…,"reason":"ask-human","started_at":…,"ended_at":…,"waiting_ms":…}`

### C2 · 返工与情绪，在每次用户输入时判断

- **错在哪**：我把返工挂在“每 N 轮/收尾”，而且是 AI 自说自话
- **改法**：**每次用户发消息时**注入一次自评要求：
  - 这次输入里，用户是否表达不满/否定（情绪）
  - 上一轮的产出是否被推翻（返工）
- **落盘**：`{"ev":"self_review","sid":…,"work_id":…,"rework":true|false,"sentiment":"pos|neu|neg","reason":"…"}`

### C3 · 收尾顺序

文字顺序本来就是：AI 认为完成 → 向用户确认 → 用户确认后 → `work_close` + `work_summary`。
飞书里那段代码块渲染歪了，改成分步列表：

1. AI 判断可以收尾
2. AI 问用户确认
3. 用户确认
4. 才写 `work_close` + `work_summary`
5. 未确认不关闭

## 注入点清单

### P1 · 首轮注入（未绑定）

**触发**：会话第一个 step，且 `bindings` 里没有本会话的 active 记录

**当前文案**（事实）：

```text
[探针] 开工前先绑定工作（一句话说给用户，不用解释规则）：
- 续接下面某条：crop switch <work_id>
- 新开一条：crop_update(phase="start", task_id="<kebab-slug>", summary="<一句话>")
没绑定之前不要开始干活。
[探针] 未完成任务（可续接）：
- a — 做A（最后活跃 …；下一步：x）
续接请沿用上面的 task_id；新任务请调用 crop_update(...)。
跟最近活跃的那条：crop switch a；都对不上就新建一条。
```

**问题**：
- 同一件事说了两遍（“续接请沿用…” 与开头重复）
- 给了两种方式（crop switch / crop_update），AI 不知道优先哪个
- 没说“先判断这是新活还是续接”，容易机械选一条

**建议文案**：

```text
[crop] 本会话尚未绑定工作。先判断：
- 是接着已有工作做 → work_claim(work_id)
- 是新的一件事 → crop_update(phase="start", goal=…)
候选（最多 3 条）：a「做A」最后活跃…；b「做B」…
拿不准就先问用户一句。
```

**期望动作**：调用一次认领/新开工具，然后对用户说一句“我在做 X”。

### P2 · 已绑定后的每轮状态行

**触发**：每个 turn 的第一个 step，且本会话有 active binding

**当前文案**：

```text
[crop] 当前工作：做A（a）；上次更新 5 分钟前。状态有变就调 crop_update 更新一行。
```

**问题**：结尾那句“状态有变就调”比较被动；AI 容易只在被提醒时才写

**建议**：改成主动式，并把灯带进来

```text
[crop] 当前工作：做A（a）｜已用 12 分钟 · 🟡 ｜上次更新 5 分钟前
```

**理由**：状态行只报事实；要不要更新由 §P4/P5 提醒负责，避免每轮都在催。

### P3 · 未绑定时的每轮提示

**补充规则（2026-11-15 定，2026-11-15 收紧）**：纯问答可以跳过；**只要打算调用工具，必须先绑定**。原措辞“一句话能答完可以不登记”被 AI 当成逃生门（采访证实：它自认“看见了但决定绕过去”），已收紧为“要么绑定，要么显式声明跳过，且跳过只限不调工具”。

**触发**：每轮首步，仍未绑定

**当前**：与 P1 相同（重复念绑定规则）

**建议**：一行

```text
[crop] 仍未绑定工作。先 work_claim 或 work_open，再继续。
```

### P4 · 黄线（工作级 10 分钟）

**触发**：本会话工作累计活跃 ≥ `yellowMin`（默认 10），冷却 `remindMin`（默认 15）

**当前文案**：

```text
[crop] 这个工作已经 12 分钟（基线 30，0.40×）。
工作：做A
请判断这次偏慢是不是合理，并调用 crop_update 写一行：
- cause="为什么这么久"
- verdict="justified"（任务本身难）或 "not-justified"（自己走错路）
```

**问题**：没有情绪价值那一句（设计三职责缺一）；“基线/倍数”对 AI 没意义，占字数

**建议**：

```text
[crop] 做A 已 12 分钟。
① 先对用户说一句人话（例如：这个比预想久，我在处理）。
② 再调 work_update 写一行：cause=为什么慢；verdict=justified（活难）或 not-justified（走错路）。
```

### P5 · 红线（单轮 30 分钟）

**当前文案**：

```text
[探针] 当前任务块已 32 分钟（红线 30）。
1. 对用户说一句简短的人话…
2. 调用 crop_update：phase="blocked" 或 "progress"，task_id="..."，summary=…，cause=…，next=…，category=…
```

**问题**：字段清单太长（一行命令式），AI 容易照抄成字段堆砌

**建议**：只给要做什么，不给字段模板

```text
[crop] 这一轮已经 32 分钟。先对用户说一句人话，然后 work_update：卡在哪、为什么、下一步。
```

### P6 · 缺报检测

**当前文案**（两档）：

```text
[crop] 上一轮跑了挺久但没有登记。如果这个工作有进展或卡点，调 crop_update 写一行。
[crop] 已经连续 N 轮没有登记工作状态。请现在调 crop_update 写一行：在做什么 / 卡在哪 / 下一步。
```

**问题**：不错，但第二档的“N 轮”模型不知道是几轮也没关系；可保留

**建议**：保持，仅把 `crop_report` 换成 v2 的工具名。

### P7 · 收尾检查（超时后无反思）

**触发**：`stop` 且本轮超过红线，且本工作没有对应的 `work_update`/`self_review`

**当前**：不存在

**建议**：

```text
[crop] 这一轮超时结束，但没有留下任何反思。补一行：这次慢在哪、下次怎么避免。
```

### P8 · 返工 + 情绪自评（每次用户输入时）

**触发**：每次 `prompt`（用户发消息）注入

**当前**：不存在

**建议**：

```text
[crop] 用户刚说了这句。判断两件事，然后调 self_review：
- 上一轮的产出是否被推翻（rework: true/false）
- 用户语气：pos / neu / neg
一句话说明理由。
```

**注意**：这条会随每个用户消息出现，必须极短（≤ 50 字），否则就是噪音。

### P9 · 完成确认

**触发**：AI 判断工作可收尾

**当前**：不存在（AI 直接 end）

**建议**（给 AI 的话，不是给用户）：

```text
[crop] 收尾前先问用户一句“这次可以收了吗？”。用户确认后再调 work_close + work_summary。
```

### P10 · ask-human 等待

**触发**：AI 调用 ask-human 类工具时

**建议**：

```text
[crop] 你正在等人回答。等待时间单独记账，不要算成任务耗时。
```

### P11 · 系统提示常驻段落

**当前文案**（`crop:protocol`）：

```text
Crop 探针协议：
- 开工先绑定工作：…
- 收到 [crop] 提醒时…
- 与当前工作无关的问题…
- 用户表示满意或明确结束时…
```

**评价**：四条规则偏长，且第 2、3 条与 P4/P5 的注入重复

**建议**：常驻段落只留三条最稳定的，动态细节交给注入

---

### P12 · 收尾沉淀（2026-11-17）

**触发**：`crop_update(phase="end")` 且没带 `sediment`

**形态**：不是 `[crop]` 注入，而是直接拼进 `crop_update` 的工具结果。理由：如果等下一轮 `agent/pre-step` 才注入，AI 可能收尾后直接结束回合，`turn/end` 会把 `pending` 清空；工具结果当场就能看到。

**文案**：

```text
[crop] 收尾了，但还没写沉淀。这条经验落到哪？
规范→AGENTS.md（一行换一行）｜方法→skill｜机械→工具｜事实→docs｜都没有→none:<原因>。
补一次 crop_update(phase="end", task_id=同一条, what="补沉淀", summary="补沉淀", sediment=...) 即可，不会重复关单。
```

**配套**：

- 常驻协议只加一行指针，不展开决策树（决策树进协议就是给所有会话收税）。
- 完整决策树放 runtime skill `crop-retro`（`ctx.skills.register`），按需加载。
- `sediment` 只记指针，正文在目标层；健康度出「沉淀闭合率」。
- 完整方法见 `docs/WORKFLOW.md` §9。

## 评价结论

| 注入点 | 当前问题 | 严重度 |
|---|---|---|
| P1 首轮 | 重复、双入口、无判断引导 | 高 |
| P4 黄线 | 缺情绪价值句、带无意义数字 | 高 |
| P5 红线 | 字段模板太长 | 中 |
| P8 返工/情绪 | 缺失 | 高 |
| P9 完成确认 | 缺失 | 中 |
| P12 收尾沉淀 | 新增（工具结果内联） | 中 |
| P11 常驻段 | 与动态注入重复 | 中 |

**共同原则**：注入只说“做什么”，不给字段模板；每条 ≤ 80 字；同一件事只说一次。
